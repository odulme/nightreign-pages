黑夜君临 BOSS 制作流程

移植别的游戏的 BOSS、用自己的模型做原创 BOSS、再把它做成夜王，三件事走同一条 S0–S12 流水线。13 个阶段各以一道出口关卡结束；关卡写明要达到的证据等级，没过关卡就不算做完。

适用版本偏移和原版 id 在 NR 1.3.3.0（PE TimeDateStamp 0x69e0dc2a）、regulation 10350000 上测得。游戏更新后要重新核对。
证据标签game-MPgamecodedatasimmodelinferred从强到弱，实心的才算证明。图例见第 6 节
占位符<MOD_ROOT> 工作目录 · <GAME_DIR> 游戏目录 · <DEV_PROFILE> 分层开发入口（.me3 文件） · <STAGE_DIR> 暂存包文件夹 · <CHR_ID> 你的角色 id · <DONOR_CHR> 动作供体 · <BEH_DONOR> 行为图供体 · <PACK> 一起发布多个 MOD 的整合包

1总览

这条流水线管的是 BOSS 本身：从"这个 BOSS 能不能做"开始，一直到一个外观、动作、攻击、音效、思考、受击和死亡都像原作（或设计稿）的身体；数值以原版为基准，再通过"先开发版、后打包"的循环发布出去。BOSS 最后放在哪里（野外、竞技场、夜王）只影响集成阶段。手册只收录在真实游玩中验证过的方法，失败只写成一行"做 X，因为 Y"。

阶段编号 S0–S12 固定不变，别的技能文档会引用它们。子阶段加后缀（S1-alt、S2a……），从不给主阶段重新编号。旧版用过 P0–P9，对应关系是：P0 = S0，P1 = S1，P2 = S2，P3 + P4 = S4，P5 = S5，P6 = S6，P7 = S7，P8 = S9，P9 = S8 / S10。

关卡怎么判

汇报时分四种状态，绝不合并。游戏里只要出现一个新的反例，之前所有的 PASS 都作废。

  1. 已构建构建脚本 PASS
  2. 已安装并读回装进开发入口，独立读回确认
  3. 测试者看到它生效在游戏里亲眼看到
  4. 测试者认可测试者说可以了

离线关卡

确定性的构建脚本 PASS + 独立读回（只改了点名的成员 / 行 / 事件 / FXR 槽）+ 本阶段要求的模型数字。它用来决定装什么，绝不用来宣布"修好了"。

游戏内关卡

测试者在开发入口里确认（这时 S3 的调试面板已经能用）。联机关卡要求 game-MP，并收齐每台机器的日志。

发布配置关卡

S7、S9、S10 要在玩家实际使用的配置下测：联机 DLL（无缝联机）、强制深夜层数的附加 MOD、同时加载的其他 MOD。只在单人开发入口里测不算数；实在做不到，就用数字说明不确定性。

推断出来的引擎语义，在每份报告里都要标成猜测，例如"方向值 1 = 向上 inferred"。

三条路线在哪里分岔

"移植"和"原创"是来源路线，决定 S1–S2 怎么做；"做成夜王"是目的地，决定 S8–S11 怎么做。中间 S3–S7 的角色工作两条路线一样，只是原创路线的攻击和 AI 靠设计，没有原作可移植。

术语速览

下文保留这些术语的原名，这里各用一句话说明。

me3
MOD 加载器。一个 .me3 配置文件（profile）按顺序加载多个包；同一路径上，后加载的包生效。
regulation.bin
游戏的参数总包，NpcParam、AtkParam、Bullet、SpEffect 等参数表都在里面。
NpcParam
NPC 参数表，一行定义一个敌人的血量、模型、AI、缩放等。
SpEffect
特殊效果行：挂在角色身上的状态 / 标记，也用来切换动作变体、阶段、倍率。
AtkParam · Bullet · BehaviorParam
攻击判定、弹体、"行为"（TAE 事件引用的攻击入口）三张参数表。
TAE
动作时间轴事件文件：在每个动作的时间线上挂事件（判定、出弹、特效、音效、转身窗口、AI 窗口……）。
FXR
特效文件；装在 sfxbnd binder 里。
EMEVD
事件脚本，管流程逻辑：开战、血条、阶段、演出、胜负。
FLVER
FromSoftware 的模型格式（网格、骨骼节点、材质、dummy）。
dummy（dummy poly）
模型上带编号的挂点，弹体、特效、判定从这里发出。
hkx · PTCH · THSH
Havok 文件（骨架、动作、物理 / 受击胶囊）；PTCH 是其中的指针修补段，THSH 是类型哈希段。
behbnd · anibnd · chrbnd
行为图包 · 动作包 · 角色包。行为图决定能播哪些动作状态。
MSB · navmesh
地图摆放文件 · 导航网格（AI 和召唤物寻路用）。
FMG · NpcName
文本表 · 敌人名字文本。
Lua · .luagnl
AI 脚本 · AI 全局名字表（随 Lua 一起重新生成）。
Wwise bank
音效包。
供体（donor）
借用其行为图、动作、特效或参数行的原版角色，如 c2130、c4510、c4373。
叠加包（overlay）
开发入口里的一个新包，每次只装一个改动。
无缝联机 · 深夜
第三方联机 MOD（Seamless Co-op） · 游戏的高难度层数（Deep Night）。
TDR · DRED
显卡超时重置 · DirectX 12 的崩溃面包屑报告，用来定位显卡卡死。
代理
帮你做构建和分析的 AI 助手。代理从不启动游戏，也不碰存档。

2阶段详解

每个阶段写明：目标、输入、具体步骤、工具和文件、出口关卡（离线能测的 vs 要测试者在游戏里确认的）、常见失败与修法、详细资料在哪。资料文件名默认在技能 nightreign-boss-port 的 references/ 目录下；夜王相关的在 nightreign-nightlord-replace 的 references/ 下。

S0

计划

动任何文件之前，先决定做什么、"做完"怎么判，以及在游戏里用什么看清发生了什么。

所有路线原创：G0 合约夜王：五个决定

输入

来源游戏（只读）或概念 / 模型（原创路线）；原版提取文件；BOSS 将来要随之发布的 profile。

工具和文件

协调文件（json / md）、带允许列表的 id 检查器、原版 AI 普查（ai_port.md §6）；每条工作线一个 STATE.md。

具体步骤

  1. 调查表（survey_and_extraction.md §1）：动作、骨骼、网格、时间轴、攻击 / 受击数据、特效、音效、AI、只存在于原作 exe 里的数字、阶段形态、辅助角色（helper actor）。
  2. 关键决定：目的地；按体型选行为图供体（donor_graph.md：人形 c2130，四足 / 飞行 c4510，普通敌人 c4373）；放在哪（原版竞技场地图块，还是自建地图块；优先自建、只让它自己的路线加载，原因见 S7）；深夜关联（7767 或 0）；夜王的切换协议（nightreign-nightlord-replace）。
  3. "忠于原作"类请求先评估可行性：尽早调查原作机制（真正的必杀判定、防御 / 掩体影子、被地形挡住的扇形、锚定目标的图案、NPC 台词），每一项写成"原作是 X；我们可以做 A / B / C"并附数字。测试者多次在简化之后又要回原作行为 game。
  4. 诊断计划（S3 里实现，diagnostics.md）：同步日志字段包括 BOSS 动作 id、位置、朝向、血量；本地玩家的位置、血量和受到的伤害；这场战斗的每一个 MOD flag（含每台机器的 worker / 锁 flag）；部位记录（基础 / 最大 / 当前）；AI 堆监测；帧时间。战斗用的 flag 要预留在日志已经覆盖的范围里。
  5. 发布配置清单：联机 DLL（无缝联机）、强制深夜层数的附加 MOD、同时加载的其他 MOD（它们的 AI 绑定，还有谁也在你的竞技场地图块里）、me3 版本。计划在这个配置下打一场校准战（S9）。
  6. 构建前先建 id 登记表：角色 id（档案字典里没有，任何同时加载的 MOD 里也没有，包括它们的开发阶段）、弹体号段、BehaviorParam 判定、AtkParam、SpEffect、特效 id、音效 id、flag、实体 id、导航网格 NameID、关键道具行、文本 id。每个范围只有一个负责人，范围只写在负责人自己那一节（有一次检查器失败，就因为另一份笔记引用了调试范围）data。
  7. 整个联合 profile 的 AI 堆预算，按世界算（ai_port.md §6）：aicommon + 开放地图格 + 竞技场地图块的脚本 + 召唤物 + 每个同时加载的 MOD 的脚本。
  8. 原创路线的 G0 合约：外形、尺寸（身高，米）、哪些部分是刚体 / 布料 / 额外肢体、动作供体家族、行为供体、预算（面数、骨骼数、贴图尺寸）、展示版要证明什么。
  9. 问测试者"做完"是什么意思：保真规则、哪些可以简化、仇恨 / 到场规则，并约定汇报用的四种状态。开一个协调文件（id、负责人、决定），每条工作线一个 STATE.md。

max HP = trunc( f32( hp × f32( 3.54 × DN × (1 + 1.2 × (n − 1)) ) ) )

3招式调试工具

一个只在开发时用的小工具，用来控制 BOSS 出哪一招。在 S3 里、第一个攻击之前做好，S4–S10 的每个测试步骤都用它。下面的设计在一个三阶段 BOSS 移植里实际做出来并在游戏里使用过 game；尖括号里的是你为自己的 MOD 选定的占位符（<DBG_BASE>、<BOSS_ENTITY>、<CHR_ID>、<DEV_PROFILE>）。

为什么要做

  • 靠打战斗去碰某一招，会浪费大部分测试时间：AI 按随机、距离、架势、阶段和冷却选招；飞行招式几分钟才来一次；第三阶段的变体要先打掉三分之二血条。测试者看一次指定招式要 5–15 分钟，而修一个问题需要从几个位置把同一招多看几次。
  • 演出和强制倒地挂在血量门槛和部位破坏上；没有工具帮忙的调试路线不可能连续两次到达。
  • 有了面板，就能按名字请求招式、带停顿重复、从选定位置观看，动作历史还能把截图和每次出招对上。原来"我觉得是左边那个"要来回好几轮，现在变成"索引 15，12:41:07" game。

架构

窗口程序

  • 一个 WinForms（或类似）小窗口，始终置顶，双击启动：从沙箱化的代理宿主里启动的进程可能跑在私有容器里，看不到游戏的共享内存。游戏用窗口或无边框模式，独占全屏会挡住置顶窗口。点面板会抢走焦点，点回游戏窗口继续玩。
  • 证明有用的控件：每个目录条目一个按钮（按架势 / 类型分页）；AI 停止（BOSS 不再自己做决定，只播放请求）；血量锁（死不了，血量最低到 1）；循环上一招，停顿从一个短列表里选（0.5 / 1 / 1.5 / 2 / 3 / 4 / 6 / 8 秒，正好 3 位）；变体覆盖（自动 / 基础 / 变体集 1 / 变体集 2，即由 animIdOffset SpEffect 选出的阶段颜色 / 强度动作集）；面向玩家、靠近、后退；停止 / 清除（取消循环和还没开始的请求，正在进行的招式会做完）。
  • 每个按钮的提示：两种语言的可读名字、AI 招式键、它播放的槽位列表（固定的，或"AI 自己选"）、有哪些变体时间轴、面板索引。
  • 关掉窗口 = 约 1.5 秒内所有调试 flag 关闭（DLL 发现心跳停了），BOSS 回到正常 AI。

通道

  • 命名共享内存（Local\<name>，4 KB），分两块：应用块（窗口想要什么）和 DLL 块（DLL 看到什么）。每块包含魔数、版本、seqlock（写的时候为奇数，读者重试）、心跳计数、写入者进程 id。
  • 应用块：空闲、循环、血量锁、变体选择、停顿码、请求计数、请求索引。
  • DLL 块：状态（正常 / 禁用及原因 / flag 存储不可用）、BOSS 是否在场（0 不在 / 1 刚出现 / 2 稳定）、HP、最大 HP、当前动作、动作变化计数 + 最近 16 个动作 id 的环、被监视 SpEffect 的位掩码（阶段、最终形态、演出进行中、部位破坏标记、变体集、待机心跳、忙碌、狂暴、架势重置）、读回的 flag 字、最后接受的请求、结果码 + 文本、写入计数。
  • 离线用两个进程测试通道：一边是用 DLL 自身核心代码的测试程序，另一边是 --selftest 模式的窗口程序；再把窗口离屏渲染成图片审阅。

DLL 桥

  • 一个工作线程，约每 50 ms 跑一次。失败即关闭：检查游戏版本（PE 时间戳 + 映像大小）以及它调用或读取的每个函数的代码字节，任何不符就记录下来并且什么都不做。旁边放一个 <dll>.off 文件即可禁用。不打代码补丁、不挂钩、不改虚表。
  • 只读地找到 BOSS（已加载竞技场地图块里的模型 <CHR_ID> + <BOSS_ENTITY>），每次读取都有保护。
  • 只写自己的 flag id，只经游戏自己的事件 flag 设置函数（第一次调用前比对设置函数和读取函数的字节），每次写都读回。规则：
    • BOSS 在已加载地图块里出现满 1 秒之前，什么都不写；
    • 窗口已连接（心跳在 1.5 秒内变过）且 BOSS 稳定时：主开关 ON，把面板状态写进 DLL 所有的 flag；否则 DLL 所有的 flag 全部 OFF；
    • 主开关最先关、最后开，AI 永远看不到写了一半的状态；
    • 一次请求 = 先写索引（7 位），再让 2 位格雷码计数器加一（每次只变一位）；AI 先读计数器再读索引；两次轮询之间按了多次只算一次请求，取最新的索引；
    • 写入读回不符，就在接下来的轮询里重试（开发版战斗脚本在地图块加载时会清一次所有调试 flag）；连续三次失败就停止这场战斗的所有写入。
  • 以整字节占用没人用的 flag（flag 存储每字节放 8 个 flag），所以游戏写的任何东西都不会被覆盖。
  • 把 HP、动作、SpEffect 掩码、flag 读回值和最后的结果报告给窗口。
  • 日志放在 DLL 旁边，每次启动重写，上限 1 MB：版本检查、特征码数量、BOSS 挂接情况、每次连接 / 断开、每个请求（索引 + 计数）、每次写入失败。

开发版战斗脚本事件

追加到已安装开发版战斗脚本的副本上，其他事件逐条指令保持不变。初始化行放在 event 0 的末尾，并且要证明 event 0 里没有任何 SKIP 能跳过它的最后一行，保证一定会运行。所有事件 Set Network Sync State(0)；角色指令只作用于 <BOSS_ENTITY>；它们读 DLL 所有的 flag，只写 EMEVD 所有的 flag。

事件运行方式做什么
加载时清空默认，只运行一次地图块加载时清掉整个调试范围（DLL 所有 + EMEVD 所有），保证没有调试状态能跨加载留存；BOSS 出现 1 秒后 DLL 会重新写入面板状态
血量锁每 0.25 秒重启主开关 AND 锁 → 反复设置 Set Character Immortality(boss, 1)，并置一个"已应用"flag；否则只有在"已应用"时才关掉不死和"已应用"。发布版脚本从不对 BOSS 设不死，所以不会误撤别的东西
变体覆盖每 0.25 秒重启演出进行中什么都不做；主开关 AND 覆盖 → 第一次轮询时记下当前有哪些变体 SpEffect，之后让每个变体 SpEffect 恰好在它的"想要"flag 为 ON 时存在（只在状态不同时设 / 清）；覆盖关闭 → 恢复一次记下的集合
存活指示主开关 ON 时每 0.5 秒重启切换一个 flag，让窗口能显示"开发版战斗脚本在运行"（能发现调试包没装上）

离线证明：读回（原事件按顺序在前，后面是新事件；其余完全相同）；再用一个只实现这些新事件所用指令的小解释器，把面板场景跑一遍。

开发版 AI 覆盖

  • 开发版 AI 绑定 = 发布版 AI 源码逐字节不变 + 末尾追加的覆盖块，打包和预编译方式与发布版绑定完全一样（重构、LuaC -s、和 ai_port.md §6 相同的证明）。断言前缀等于发布版源码，并且这个 chunk 不新增任何全局变量。
  • 覆盖块包装发布版 AI 的几个函数（决策入口 Think、看门狗、距离检查、播放辅助函数）。主开关 OFF 时，每个包装函数用同样的参数调用发布版函数：没有随机抽取、没有 goal、没有状态写入，每次决策 / 更新只读一次 flag。证明方法：在开发版源码和开发版字节码上，跑很多次决策，子 goal 轨迹和每个 BOSS 的状态都与发布版 AI 逐字节相同 sim；然后在 flag 打开时测每个面板操作。
  • 用 ai:IsEventFlag(<DBG_BASE> + n) 读 flag，多位数字一位一位拼起来。每个 BOSS 的状态放在 ai:SetStringIndexedNumber 里（看到的序号、请求索引、循环阶段、一个在主开关上升时重置的"已武装"标记）。
  • 请求处理：
    • 在 battle goal 的下一次决策时接收；如果 BOSS 正站着待机（有待机心跳、没有忙碌标记），新请求会立刻结束当前决策；正在进行的招式从不打断；
    • 通过 AI 自己的攻击路径播放（预转身或后退、架势切换、旋转、攻击后的 goal），所以转身、弹体和特效都是 AI 自己的；即使 AI 的距离检查会拒绝，请求的招式也照样播放；
    • 每个键对应一个固定的槽位列表，或"AI 自己选"（例如按目标在哪一侧选左 / 右成员）；
    • 控制动作用通用 goal（GOAL_COMMON_Turn、ApproachTarget、LeaveTarget），先从低架势起身；
    • AI 停止 = 不做自己的决定（短等待，必要时从低架势起身一次）；
    • 循环：招式结束后等选定的停顿，再播一次。
  • 从不碰演出：演出 SpEffect 存在期间，覆盖块和发布版 AI 一样让路。

预留 id，以及怎么保证它不进发布

  • flag：在竞技场 flag 组里一个没用过、有存储（world 类）的范围内，预留 32 个 DLL 所有 + 8 个 EMEVD 所有的 flag，按整字节对齐。事件：同一组里 4 个开发事件 id，和所有 flag 不相交（事件 id > 299 在结束或重启时会置位 flag "id + slot"）。
  • 认领前先扫描 flag：覆盖每一层的每一个 EMEVD（原版脚本、自己的每个开发包和发布版、同时加载的 MOD 的发布版和开发阶段）：每个解码出的整数参数都算（是实体 / 区域 / flag id 的超集）、每个事件 id、每个 Initialize Event 的"事件 id + slot"、每条批量 / 范围指令覆盖的区间；再加上 AI 源码、DLL 的 ini（flag 列表）和 id 认领文档。报告已用的号码、覆盖它们的范围和空闲的整字节；构建时断言认领的 id 空闲且填满空闲字节。
  • 扫描也会数文字：调试范围只写在 id 登记表的调试小节里（扫描会跳过它自己那一节），别处一律不写：其他笔记、readme、技能文档都不写。有一次检查器失败，就是因为另一份笔记引用了调试范围。
  • 开发专用包始终放在 <DEV_PROFILE> 最后，下面的战斗脚本或 AI 绑定一变，就用它的构建脚本重建：构建脚本读取 <DEV_PROFILE>，找出实际生效的开发文件（后加载的包生效），断言它们的哈希等于预期的基础（换新基础要显式打开允许开关）；已经加载了调试包就拒绝；只写入自己的工作文件夹和一个新的 DLL 文件夹（路径守卫拒绝发布 / 阶段 / 钉文件 / app-data 路径）。如果重建改变了已证明的 DLL 二进制，放回在游戏里证明过的那一份。
  • 发布守卫：钉文件工具只接受符合发布命名规则的包，profile 里还有调试 / 探针块时直接拒绝（从不悄悄跳过）；发布用的 natives 文件夹只接受列出的 DLL；调试构建的最后一步证明钉文件、发布 natives 和基础 profile 文件里都没有提到任何调试文件或哈希，并且发布载荷里的战斗脚本 / AI 绑定和调试版不同。每个调试文件都以 _DEBUG 结尾命名，旁边放一个"仅开发用，绝不发布"的 readme。
  • 联机测试那天谁都不用调试 profile；面板是单人开发工具。

它做不到的事（以及怎么绕过去）

  • 演出和血量门槛上的特殊招不在范围内：演出 SpEffect 存在时覆盖块让路，特殊招是战斗脚本发起的，不是 AI。到达方法：AI 停止 + 把血打到门槛。血量锁挡不住门槛（不死只是让血量最低到 1，比例门槛在血量经过时照样触发），血量锁的用途是在特殊招之后保住 BOSS，不是避开特殊招。外部伤害倍率能很快打到门槛，但那一场就不能用来做平衡和部位破坏校准了（它放大血量伤害，不放大部位伤害；params_balance.md §9）。
  • 请求要等下一次 AI 决策：倒地、架势崩溃和强制动作期间什么都不会开始。
  • 开发版战斗脚本走的是 DEBUG 路线，显示不了 REAL 路线的行为（远征状态、结算、联机）。
  • 它代替不了目的地测试（真实远征），也代替不了真实联机。

开发版叠加包工作流

  1. 每个包一个改动，放在新文件夹里，追加到 <DEV_PROFILE>，load_after 指向上一个最顶层的包（同一路径上后加载的包生效；me3 日志里的 override= 行能证明实际用的是哪一份）。从不覆盖已安装或已暂存的文件夹：这些文件夹就是回退历史。
  2. 每个改动一个构建脚本：断言自己的基础，只按确切的旧值改自己的单元格 / FXR 槽 / 事件（"单元格模式"）。这样输出可以按任意顺序叠加，几个代理可以并行工作，同一个构建脚本也能在发布输入上重放。
  3. 安装守卫：游戏在运行时拒绝（忽略 0 线程的僵尸进程）；暂存哈希不是验证过的那个时拒绝；当前最顶层包不是预期的那个时拒绝；目标文件夹已存在时拒绝。备份 profile；下一次构建断言新的最顶层。
  4. 调试包只用于开发、始终放最后，战斗脚本或 AI 绑定一变就重建（发布工具只会追加，所以之后发布相同路径的包会遮住它，或被它遮住）。步骤：移除它的块，把下一个块的 load_after 改指向前一个，安装新包，在新基础上重建调试包，再把它加回最后。如果重建改变了已证明的 DLL 二进制，放回游戏里证明过的那一份。
  5. 探针（只写日志的部位血探针、可见标记、测试道具）放在 --probe / 开发开关后面构建，在状态文件里标"绝不打包"；装着探针的时候绝不运行钉文件生成器。
  6. 每个功能的顺序：
    1. 只读研究
    2. 构建到暂存文件夹
    3. 独立验证
    4. 装进开发版
    5. 测试者游玩
    6. 从开发版顶层做发布构建
    7. 和上一版做发布差异
    8. 打包
    9. 补丁
  7. 通过自身离线检查的开发补丁直接安装，不再单独审计，由测试者在游戏里验证。给别人的东西做一轮审计 + 一次复核。
  8. 每次改共享工具，都在原文件旁边备份；每一轮把用到的工具复制进这一轮的新文件夹。

  • 绝不根据参数、菜单或推断断言原版或引擎机制：标 inferred 并问测试者。测试者比文件更了解原作和 NR，保真问题由他拍板。
  • 游戏里失败之后，不要在一个从没见过它生效的部件上再叠一个纸面原因：用本次移植里已经证明过的部件重建，并对照测试者日志位置的回放来验证。
  • 两次纸面解释失败后，要一段录像。

先开发版，后打包

每个改动都要先在开发 profile 里确认，再打包，包括大厅关键道具这类只在整合包层存在的功能（给它们做一条开发版路线）。两次功能直接进了发布版，两次发布都失败了。

一招什么时候算完成

  • 原作动作链完整，没被过早的 AI 窗口截断；
  • 朝向和原作一样：只在原作转身处转身，瞄准射击会重新瞄准；
  • 命中时机 = 视觉时机；命中范围 ≤ 显示范围；矮个角色能被打中；
  • 除非是有意的范围攻击，否则能翻滚躲开；
  • 特效（可读、在显卡预算内）和音效都在；
  • AI 选它的频率和原作一样；
  • 而且测试者这么说了。
